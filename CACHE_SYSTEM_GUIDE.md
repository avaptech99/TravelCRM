# CRM 3.0 Modernized Cache System Guide

This document explains the new caching architecture implemented for Travel Window CRM 3.0, designed to maintain high performance under a 512MB RAM constraint and support 20+ simultaneous users.

## 1. Architecture Overview

The system uses `node-cache`, a high-performance internal RAM cache. Unlike the previous implementation, this version is **centralized**, **typed**, and **event-driven**.

### Key Components:
- **Centralized Registry (`CK`)**: All cache keys are generated by a central builder. This prevents "cache fragmentation" where different parts of the app use different names for the same data.
- **Auto-Invalidation (`CacheInvalidation`)**: A "Smart Busting" system. When a booking is updated, the system automatically knows exactly which lists, stats, and individual caches need to be cleared.
- **Proactive Warm-up**: On server start, the system pre-fetches dropdowns and agent data so the first user of the day doesn't experience a "cold" (slow) load.

## 2. Scalability (Handling 20+ Users)

The cache is split into two categories to maximize efficiency:

| Data Type | Scope | Benefit for 20 Users |
| :--- | :--- | :--- |
| **Shared** (Dropdowns, Agents) | Global | Loaded **once**; all 20 users benefit from the same RAM object. |
| **Private** (My Bookings, Notifications) | Per-User | Cached by `userId`. Even with 20 users, these small lists only take ~10MB total. |
| **Heavy Stats** (Analytics) | Global/Param-based | Expensive calculations are cached for 2-5 minutes, preventing 20 users from hitting the DB at once. |

## 3. How to Verify It's Working

### Method A: The Network Header (Visual Check)
1. Open the CRM and go to **All Leads**.
2. Open **F12 Dev Tools** -> **Network**.
3. Click an API request like `GET /api/bookings?page=1...`.
4. Look for the `X-Cache-Status` header:
   - `MISS`: Data was fetched from MongoDB (Expected on first load).
   - `HIT`: Data was served from RAM in <10ms (Expected on refresh).

### Method B: The Admin Stats Endpoint
You can check the "Live Brain" of the cache by calling this endpoint (requires Admin login):
**URL**: `https://travelcrm-2-0.onrender.com/api/settings/cache-stats`

#### What to look for:
- **`cache.hits`**: This should be significantly higher than `misses` after an hour of usage.
- **`memory.rss`**: This is your physical RAM usage. It should stay stable (e.g., 100MB - 150MB) and not climb indefinitely.
- **`uptime`**: How long the server has been running without a crash/restart.

## 4. Technical Guardrails
- **TTL (Time To Live)**: Most data expires automatically after 30-120 seconds if not used, keeping RAM fresh.
- **Max Keys (1,000)**: If users generate too many unique filter combinations, the oldest ones are deleted to prevent "Out of Memory" crashes on Render.
- **Cloning Disabled**: The cache stores references directly. This is 10x faster and uses 50% less memory than standard caching.
